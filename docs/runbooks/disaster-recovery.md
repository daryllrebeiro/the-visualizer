# Operational Playbook — Disaster Recovery & Backup Procedures

This runbook outlines the processes for database backups, point-in-time recovery (PITR), object storage restoration, and failover targets for the Visualizer platform.

---

## 1. Objectives & Targets
* **Recovery Point Objective (RPO)**: < 1 hour. No more than 1 hour of transaction data can be lost in a major disaster.
* **Recovery Time Objective (RTO)**: < 2 hours. Service must be fully restored within 2 hours of a declared disaster.

---

## 2. Database Backup & Restore

### 2.1 Automated Cloud SQL Backups (Production)
Cloud SQL PostgreSQL is configured with:
* **Automated Daily Backups**: Enabled at 03:00 UTC.
* **Point-in-Time Recovery (PITR)**: Enabled, retaining 7 days of write-ahead logs (WAL).
* **Backup Retention**: 30 days of automated backups retained.

### 2.2 Manual Backups (Ad-hoc / Maintenance)
Before executing database migrations or high-risk schema updates, run a manual backup using the provided script:
```bash
# Set credentials (if different from default local env)
export DATABASE_URL="postgresql://user:pass@host:5432/dbname"

# Run backup script (saves compressed gzip in ./backups)
./scripts/db/backup.sh
```

### 2.3 Manual Database Restoration
To restore a database dump generated by the backup script:
```bash
# Execute restore script specifying target backup file
./scripts/db/restore.sh ./backups/backup_20260820_120000.sql.gz
```
> [!CAUTION]
> The restore script drops the active `public` schema CASCADE before applying the backup. Never execute this on a production database unless you explicitly intend to overwrite its entire state.

---

## 3. Google Cloud SQL Point-in-Time Recovery (PITR)

If data is corrupted or deleted accidentally (e.g. bad application deploy or malicious activity), use PITR to clone the database to a specific millisecond timestamp:

### 3.1 Via gcloud CLI
```bash
# Clone production instance to a new restore instance at specified time
gcloud sql instances clone visualizer-db-production visualizer-db-restored \
  --point-in-time "2026-08-20T12:30:00.000Z"
```

### 3.2 Post-Recovery Steps
1. Verify the integrity of the data in `visualizer-db-restored`.
2. Update the environment configuration of the Hono API server (`DATABASE_URL`) to point to the new database connection string.
3. Once verified, promote the restored instance or drop the corrupted instance.

---

## 4. Cache & Session Recovery (Redis)
Redis is utilized exclusively for ephemeral data: rate-limit buckets, topology locks, active session tokens, and the simulation runner's immediate event queue.

### 4.1 Redis Failure Scenario
If the Redis Memorystore instance fails or is destroyed:
* **Session State**: Active visualizer user sessions will be disconnected.
* **Self-Healing**:
  * Users' UI will immediately initiate connection retries to the WebSocket Gateway.
  * The Hono API and WebSocket gateways reconnect to Redis automatically once it comes back online.
  * Permanent user, organization, and topology definitions are safely stored in PostgreSQL and will not be lost.
* **Action Plan**:
  * If Redis doesn't automatically recover, recreate it using Terraform:
    ```bash
    terraform target google_redis_instance.redis
    terraform apply -auto-approve
    ```

---

## 5. Simulation Replays & GCS Bucket Recovery
* **Versioning**: GCS replay buckets have object versioning enabled. If a replay file is deleted, you can fetch its historical version via the console or `gcloud storage`.
* **Lifecycle Rules**: Storage costs are minimized by a 30-day auto-deletion policy on simulation replays.
* **Permanent Topologies**: Topology layout structures are stored inside PostgreSQL as `JSONB` definitions. Replay assets can always be re-simulated from the original seed and topology layout.
